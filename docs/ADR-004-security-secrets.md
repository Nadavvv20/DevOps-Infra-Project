# ADR-004 — Security & Secret Lifecycle

## Status
Accepted

## Context

Secrets (database passwords, Redis AUTH tokens, API keys) must never be stored in Git, application images, or plain Kubernetes Secrets created by hand. We need an end-to-end secret lifecycle that spans Terraform provisioning → AWS Secrets Manager storage → Kubernetes runtime injection — with full auditability and zero long-lived credentials.

---

## Threat Model

| Threat | Mitigation |
|---|---|
| Secret in Git history | Secrets generated by Terraform `random_password`, stored in Secrets Manager — never in `.tf` files or committed to Git |
| Stolen EC2 instance credentials | IRSA scopes IAM to a specific Kubernetes service account; instance metadata tokens are not used by pods |
| Excessive IAM permissions | ESO IRSA role permits `secretsmanager:GetSecretValue` only on specific ARNs (least-privilege) |
| Kubernetes Secret exfiltration | Secrets stored as base64-encoded K8s Secrets — encryption at rest enabled via AWS KMS on EKS (envelope encryption) |
| Man-in-the-middle on secret refresh | ESO communicates to Secrets Manager over TLS; pod mounts are tmpfs |

## IRSA Deep Dive

### How IRSA Works (Interview-Critical)

IRSA (IAM Roles for Service Accounts) is the mechanism that allows a Kubernetes pod to assume an AWS IAM role **without storing any static AWS access keys**.

**Mechanism:**
1. EKS creates an OIDC provider endpoint per cluster: `https://oidc.eks.il-central-1.amazonaws.com/id/CLUSTER_ID`
2. Every pod with a properly annotated ServiceAccount gets a **projected volume** — an OIDC-signed JWT token at `/var/run/secrets/eks.amazonaws.com/serviceaccount/token`
3. The AWS SDK in the pod (or the ESO binary) calls `sts:AssumeRoleWithWebIdentity` with this JWT
4. AWS STS validates the JWT against the OIDC public key, checks the IAM Trust Policy `Condition` (must match namespace + service account name), and returns short-lived credentials (1 hour TTL)
5. The SDK auto-refreshes credentials before expiry — no manual rotation needed

**IAM Trust Policy structure (generated by Terraform):**
```json
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/oidc.eks...." },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "oidc.eks.../id/CLUSTER_ID:sub": "system:serviceaccount:external-secrets:external-secrets-sa",
      "oidc.eks.../id/CLUSTER_ID:aud": "sts.amazonaws.com"
    }
  }
}
```

The `sub` condition pins the trust to exactly one ServiceAccount in one namespace. A compromised pod in a different namespace cannot assume this role.

## Alternatives Considered

### Option A: Kubernetes Secrets committed to Git (Rejected)

Plaintext base64 is not encryption. `git log` exposes secrets permanently even after deletion. No rotation workflow. **Hard no.**

### Option B: Sealed Secrets (Bitnami)

Encrypt secrets with cluster's public key; store `SealedSecret` CRD in Git; controller decrypts on apply.

**Pros:** Secrets live in Git alongside manifests — true GitOps purity.  
**Cons:**
- If the cluster's private key is lost, all secrets are unrecoverable
- Rotation requires re-encrypting and committing a new SealedSecret
- No centralized audit log of who accessed what secret

**Verdict:** Viable for single-cluster small teams. Loses to ESO+Secrets Manager at scale where audit trails and cross-cluster secret sharing matter.

### Option C: HashiCorp Vault + Vault Agent Sidecar (Rejected for this stack)

Full-featured secret management with dynamic credentials, PKI, lease renewal.

**Pros:** Dynamic short-lived database credentials (Vault issues a new DB user per pod start).  
**Cons:**
- Vault itself becomes a highly available, operationally complex stateful service (etcd + raft storage)
- Adds 3-5 additional EC2 nodes or ECS tasks just for the secret backend
- Overkill when AWS Secrets Manager + IRSA provides 90% of the security value at 10% of the ops cost

**Verdict:** Recommended for 200+ person orgs with multi-cloud or on-prem requirements. Over-engineered here.

### Option D: External Secrets Operator + AWS Secrets Manager (Chosen) ✅

Lightweight operator (single Deployment), leverages AWS-managed storage, native IRSA integration, rotation-aware refresh interval, and centralized CloudTrail audit logging of every `GetSecretValue` API call.

## EKS Envelope Encryption

Kubernetes Secrets are stored in etcd, which EKS backs with AWS-managed KMS encryption by default. We additionally enable **envelope encryption** — each Secret is encrypted with a per-secret Data Encryption Key (DEK), which is itself encrypted by a KMS Customer Managed Key (CMK):

```hcl
# In the EKS cluster config
encryption_config = [{
  provider = { key_arn = aws_kms_key.eks.arn }
  resources = ["secrets"]
}]
```

This means: even if someone gets raw etcd access (e.g., via a misconfigured backup), they cannot read Secret values without KMS access.

## Secret Rotation

| Secret | Rotation Method | Frequency |
|---|---|---|
| Aurora password | Terraform + Secrets Manager rotation Lambda | 30 days |
| Redis AUTH token | Terraform `random_password` + taint | Manual (or Secrets Manager auto-rotate) |
| GitHub Actions PAT | Manual via GitHub + stored in GH Secrets | 90 days |
| ArgoCD admin password | Auto-rotated via ArgoCD `argocd-initial-admin-secret` | Post-initial-setup |

**CloudTrail Audit:** Every `secretsmanager:GetSecretValue` call is logged with caller identity (the IRSA role ARN), source IP, and timestamp — providing a full access audit trail without additional tooling.
